# Interface quality gate

Every new or changed screen and control must pass this gate before the work is called complete. Apply it to both the architecture map and execution map, the project window, dialogs, menus, and future clients. Visual fashion is reviewed for usefulness and consistency; it is not an objective compliance score.

1. **Understandable structure.** Give each view a clear primary task, visible hierarchy, familiar action names, and logical grouping. Keep primary actions easy to discover. Use progressive disclosure for advanced details. Do not make a gesture, color, icon, or context menu the only way to understand or perform an action.
2. **Predictable interaction.** A single click selects, a double click opens or closes the node's main detail, and a right click opens contextual actions. Drag selection has a visible mode and a non-drag alternative. Destructive or meaningful study changes have undo and redo. Preserve the user's position and focus when details open or close.
3. **Readable states.** Check light, dark, and system themes. Text, selected and focused states, disabled controls, group boundaries, edges, warnings, and menus must remain distinguishable. Use text or shape along with color for status. Respect reduced motion and at least 200% zoom without hiding essential controls.
4. **Accessibility baseline.** Meet [WCAG 2.2 AA](https://www.w3.org/TR/WCAG22/) for changed UI: keyboard operation, visible focus, text contrast at least 4.5:1, meaningful non-text contrast at least 3:1, pointer targets at least 24×24 CSS pixels or a documented exception, and an alternative to dragging. Use semantic controls and accessible names; ensure context menus work from the keyboard and close with Escape.
5. **Verification gate.** Add focused tests for interaction and state restoration. Review the affected screen with pointer and keyboard at normal and 200% zoom in both themes, including empty, loading, error, selected, expanded, and disabled states where relevant. Run the UI tests and typecheck; run the native window check for changes to canvas interaction. Verify the actual application artifact the user launches: `npm run build` updates `carma/_ui`, while `dist/CARMA` and an already open WebView keep their previous UI until updated and restarted. Record any failing criterion and resolve it before claiming completion. Automated tests cannot alone prove accessibility or ease of use.

The project specification in `docs/carma-spec.md` records feature-level acceptance criteria. This file is the tracked rule for every future UI change.
